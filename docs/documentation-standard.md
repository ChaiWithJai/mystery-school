# Documentation standard

This repository adapts HashiCorp’s public documentation guidance. It does not claim HashiCorp certification or a universal README specification.

Use [HashiCorp’s core writing guidance](https://github.com/hashicorp/web-unified-docs/blob/main/docs/style-guide/top-12.md) and [command organization guidance](https://github.com/hashicorp/web-unified-docs/blob/main/docs/style-guide/codeblocks-and-consoles/organization.md): active voice, present tense for existing functionality, direct instructions, specific contextual links, and prose explaining a command before its code block.

## Organize for the reader

Keep the README focused on purpose, first use, runtime requirements, and navigation. Put procedures in task guides, implementation boundaries in reference pages, and dated test results in evidence records. Separate product intent from implemented behavior. Avoid unexplained acronyms, repeated history, and claims such as “perfect,” “instant,” or “proven” without evidence.

## Review a documentation change

Check every relative link and documented command against the reviewed revision. Name prerequisites and the expected result. Distinguish local, hosted, live-model, and recorded modes. Include provenance for imported code and media. Keep historical evidence tied to its original revision; do not silently upgrade its claims when the product changes.

Use descriptive headings and link labels. Introduce tables and code blocks with explanatory prose. Keep secrets, machine-specific credentials, and private participant data out of examples. A passing documentation review does not establish event eligibility or media rights.
